How analysis starts and reports are delivered

Source revision: 6a19ea297bb219509c994780c96bdd6ce6c4bfab, inspected 2026-10-20. This page describes the checked-in implementation. It does not attest to the current running service, deployed binary or live debugger/model qualification.

Discovery records eligible dump identities. Automatic scheduling claims only the configured analyzer version; manual analysis enters the same acquisition pipeline directly. Durable report delivery has its own loop, so disabling automatic analysis or running a job does not suspend pending publication when write-back is enabled.

Identity, reuse and queues

A job identity is (dumpId, inputSha256, kind, analyzerVersion). Rich reports additionally bind the analyzer name, carry a stable r2_ report ID and digest, and are immutable. The default analyzer version is 0.2.0; configuration rejects the legacy compact-capture identity 0.1.0. Discovery, manual analysis and explorer overlays share the configured version. Use a distinct version for intentional new evidence or a changed capture profile.

After the catalog availability/hash gate, a manual request returns the existing rich report projection under the same identity before registering a run. It rejects a same-identity legacy compact report and requires a new version for rich reanalysis. An existing rich report attributed to another analyzer name is an integrity conflict. Repeating an analysis request therefore does not force re-execution or overwrite captured evidence.

The durable discovery inventory is broader than the operator queue. Queue reads include only claimed, fetching, staged, analyzing and reporting; they exclude discovered candidates and terminal rows. Active manual runs are tracked separately and merged into the dashboard queue. The explorer browses the ledger catalog independently and overlays current-version local phases. A large catalog or discovered inventory does not mean that many analyses are running.

Control switches

SettingBehavior
DUMP_ANALYZER_SCHEDULER=on (default)Resumes and claims current-version jobs, one scheduled job at a time.
DUMP_ANALYZER_SCHEDULER=offBoot scan/recovery, feed, dashboard and manual actions still operate. The automatic scheduler claims and resumes no jobs. Delivery still runs if write-back is on.
DUMP_ANALYZER_WRITE_BACK=on (default)Enables ledger publication and boot/periodic delivery of pending reports.
DUMP_ANALYZER_WRITE_BACK=offTreats the ledger as a read-only dump source. Reports save locally and reporting jobs settle locally; no analysis publication attempts run. This switch does not disable automatic acquisition.
DUMP_ANALYZER_POLL_INTERVAL_MSDefaults to 10,000 ms; accepted range 5,000–30,000 ms. Controls feed idle polling and scheduler idle sleep, separate from the 60-second delivery cadence.
DUMP_ANALYZER_HTTP_ADDRDefaults to 127.0.0.1:4180. Empty disables the HTTP listener.

Local actions and credentials

At boot, DUMP_ANALYZER_TOKEN wins and is persisted as the latest-used ledger token; otherwise the daemon loads the stored token. Boot fails if neither exists. The token is an outbound DumpLedger credential. The token-store routes validate a candidate against the ledger before saving it and updating the HTTP action digest.

Analysis and rescan JSON actions accept a matching Authorization: Bearer … header. An absent header uses the daemon's configured token if one exists; an explicitly wrong scheme or wrong token rejects. Form actions require a token field, whose empty value also selects the configured token. Without a configured token, guarded actions reject. These fallback rules permit local actions without retyping the saved credential; they do not authenticate the caller of a publicly exposed listener.

Dashboard/report reads are unauthenticated, and token-store routes do not require an existing local token. Loopback is the default listening scope. A deployment that exposes this listener beyond its intended local audience needs its own caller-access controls; the outbound ledger credential is not such a boundary.
